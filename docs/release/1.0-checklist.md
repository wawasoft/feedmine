# FeedMine 1.0 Release Checklist

Release branch: `release/1.0`
Hardening branch: `fix/release-1.0-final-hardening`
Base snapshot: `8e684a3a36bbd5ecc3eb037c60f577800e470311`
Target version/build: `1.0 (6)`

This file is the single release checklist for FeedMine 1.0. Until submission, work on `release/1.0`; do not merge old feature branches and do not add new product features.

## Scope lock

### In 1.0
- Welcome → Composer → Feed onboarding
- Start Broad
- Main timeline
- Catalog/source search and Source View
- Text, podcast and video playback
- Bookmarks
- Add feed/URL
- OPML import
- Essential filters
- Curated/personal feed
- Collections, provided smoke tests remain clean
- Smart Feeds/Smart Bookmarks in foreground
- Cached/offline launch behavior already present

### Deferred from 1.0
- Smart Feed background refresh (`BGAppRefreshTask`)
- Explicit download/offline manager
- Share Extension revival
- iCloud sync
- Large architecture/refactoring work
- GitHub Actions / hosted CI

- [x] Keep the catalogue and taxonomy work off the main actor (the other half of finding 3:
      "nenhuma tarefa de catálogo/disco monopolizando o MainActor por mais de 100 ms")
      — once the local page painted at ~2 s the app *looked* ready and then ignored taps, which the
      simulator's accessibility queries exposed as `Timed out while evaluating UI query`. The app's own
      signposts bracketed `OPML.load` at 7.6 s and `Taxonomy.loadOrBuild` at 1.7 s, and **that reading was
      too coarse**: a `sample` of the process during startup (2026-09-16) shows the main thread inside
      `mach_msg` for 4678 of 4714 samples — idle in its run loop — while the catalogue work
      (`FeedStore.start()` → `SourceRegistry.loadFromOPML()` → `OPMLParser.fullParse` →
      `deduplicateSources` → `decodeURLXMLEntities`, i.e. regex over every URL) runs on
      `DispatchQueue_18: com.apple.root.user-initiated-qos.cooperative`. So the signpost span did not mean
      main-thread occupancy; what did monopolise the main actor were the two *derivations* below, which
      ran synchronously inside those spans. The outer spans were never going to shrink — measure
      main-actor occupancy, not wall time. Both derivations moved off the main actor and the main actor
      now only assigns:
      - `SourceRegistry.deriveCaches(from:sharedCountrySourceURLs:)` — pure and `nonisolated`: the
        77,443-entry pass building `sourceByURL`, language counts, topic regions, the country/topic key
        sets and the category map, plus the shared-country URL intersection. `loadFromOPML()` computes
        it in a detached task and hands it through the new `preparedCaches` slot when it assigns
        `sources`; `rebuildCaches()` is now `applyCaches(deriveCaches(...))`, so both paths share one
        derivation and cannot drift.
      - `TaxonomyStore.prepareCache(from:sharedCountrySourceURLs:)` — fingerprint, cache read, JSON
        decode, children/reverse index rebuilds and coverage groups. `loadFromCache` is now `async` and
        awaits it in a detached task, applying the result with `applyPreparedTree`; the coverage-group
        computation is shared with `build()` as `coverageGroups(flatIndex:nodeToFeedURLs:)`.
      The `sources` `didSet` keeps its original behaviour for every other writer (the prepared slot is
      consumed once, then the normal rebuild runs), and `sortedChildrenCache` is still invalidated on
      the warm-cache path.
      Measured after: `OPML.load` 7.58 s wall (its detached share included) with the main actor free,
      `Taxonomy.loadOrBuild` 1.71 s wall, and the two journey tests that regressed against the early
      paint pass again on a healthy device.
- [x] Key the cached page by the composition that produced it (finding 8)
      — the restore path took no filter signature, so a page cached under one composition could be
      restored under another; and the signature-keyed variant could never have worked, because
      `pageCacheURL` hashed the signature with `hashValue`, which Swift seeds per process — a file
      written by one launch was unreachable from the next.
      `pageCacheURL(filterSignature:)` now hashes with SHA-256 (prefix of the hex digest as the file
      name), `FeedStore.pageCacheSignature` is the stable identity of the composition (preset
      `cacheKey`, region, content type, languages, mood, source filter, taxonomy-node filters and the
      content-filter set — the click/consumed history is excluded on purpose, since it changes on every
      interaction), `setVisibleItems`/`publishCards` carry it to `cacheVisiblePageIfNeeded`, and both
      restore sites read with it. `PresetSelector.cacheKey` was added for this: `displayName` is
      user- and locale-dependent, so a renamed collection would have orphaned its cache.
      Verified across processes on the simulator: launch 1 wrote
      `visible-page-cache-ded4e5c9ca86067f0ea8eba88f7decfc.json` and launch 2 restored it — the restored
      page was the app's first rendered frame (≈0.7 s, Release, visually confirmed as the feed) — i.e. the
      signature is stable across launches and write/read agree.
- [x] A filter change presents its matching local articles instead of waiting for the network (finding 5)
      — `setFilter` clears the visible set and marks `.preparing` + `.refreshing`, and `publishCards`
      then refused to leave `.preparing` while `.refreshing`. The flush did hydrate from SQLite first,
      but the phase stayed on the loader until the *network* fetch returned, so changing a filter with a
      slow or unreachable server showed a spinner while matching articles sat in the database — the
      acceptance criterion "com conteúdo local válido, nenhuma dependência de rede para a primeira
      página ou aplicação de filtro" was not met.
      The flush now settles `.ready` as soon as the local reload published a non-empty composition
      (`[TaxonomyTrace] flush gen=… local page published items=…`), and the fetch keeps appending in the
      background; the terminal state below is unchanged and still decides `.empty` only when nothing was
      found at all. The language-buffer branch already behaved this way, so the fix generalises an
      existing pattern rather than inventing one.
      Guarded by `FeedStoreTests.testFilterChangeShowsMatchingLocalArticlesWithoutANetwork`, which seeds
      five local articles from an enabled catalogue source, applies a filter with no reachable server
      and requires the published `.ready` page — verified in both directions: it fails with the fix
      disabled (54.4 s, poll exhausted) and passes with it (22.2 s, trace `loaded=5 filtered=5` →
      `local page published items=5`).
- [x] Stop rebuilding the disabled-source index on every filter path call (finding 2)
      — `buildFilterInput` walked `registry.sources`, asked `isSourceEnabled` for each and normalised
      every URL, on the main actor, **on every call** — so each filter pass and each append during
      scroll paid catalogue-sized work: measured with the full catalogue loaded, twenty filter passes
      cost **61,743 ms** before the change (≈3.1 s each) and **0.8 ms** after. The snapshot is now built
      once and cached on `registry.sourceRevision` + `registry.enablementRevision`.
      The cache is only correct if every enablement change invalidates it, so that was checked rather
      than assumed — and the check found the revision was **not** usable for it. All six mutating entry
      points (`setRegionEnabled`, `setCategoryEnabled`, `toggleSource`, `setTopicRegionsEnabled`,
      `resetAllToggles`, `setAllCountriesEnabled`) do call `invalidateActiveCounts()`, but that function
      does not bump `enablementRevision`: it sets `activeCountsAreCurrent = false` and schedules
      `recomputeActiveCounts()` through `DispatchQueue.main.asyncAfter(.now() + 0.12)`, and the bump lives
      inside that recompute — so the revision lagged a bulk toggle by ~120 ms, and `resetAllToggles` could
      skip the recompute entirely via `ensureActiveCounts()`'s early return.
      The first attempt was to bump inside `invalidateActiveCounts()`. **That was wrong and was reverted**:
      the bump then advertises a new revision *before* the counts it describes are recomputed, and
      `LanguageCountSnapshot` (`SourceRegistry`) hands revision and counts to `FeedLoader` together — a
      consumer pairing the two would read a mixture. Two store tests failed on that build
      (`testFilterChangesWhileCollectionActive`, `testFilterGenerationPreventsStaleOverwrite`), and while
      they also pass standalone (so they are in the load-sensitive family, not a hard regression), the
      reverted line is the honest shape: a revision means "the state with these counts", and it must be
      published where those counts are.
      What invalidates the cache instead is the state itself: the snapshot compares copies of
      `registry.disabled` and `registry.enabledOverrides` (each set separately, so a source moving from one
      to the other is caught) and rebuilds when either differs. That cannot lag, because it *is* the state,
      and it costs a set comparison per filter pass against a 77k-source walk.
      Guarded by `FeedStoreTests.testFilterPassSeesSourceToggleImmediately`, which toggles a real
      catalogue source off and back on and requires the very next pass to follow — the failure mode a
      stale snapshot would produce.
- [x] Take the SQLite hydration's filter and balance off the main actor (finding 7)
      — after the async SELECT returned, `reloadFromSQLite` filtered up to ~5,000 candidates and
      balanced them on the main actor, through predicates that normalise text and strip HTML. Both steps
      are pure, so they now run in the off-main pass (`applyFiltersAsync` plus a detached
      `balancedCandidatePool`), and the composition context (`ctx`, `filterGeneration`,
      `presetGeneration`) is captured *before* those new suspensions, per the contract finding 6
      established. The legacy pipeline's two `applyFilters` calls in the same function moved the same way.
      Making this swap required fixing a divergence it exposed: the off-main pass was **stricter** than
      the main-actor one. `isSourceEligible` treats an explicit catalogue query — a content-type filter,
      or a taxonomy selection that names the source — as bypassing *inherited* disables (category,
      region) while still respecting a source turned off by hand; the off-main pass had only the combined
      disabled set, so `testAcousticsEndToEndLocalPipeline` dropped all four of its items
      (`loaded=4 filtered=0`). `FilterInput` now carries `explicitlyDisabledSourceURLs` (built in the same
      revision-keyed walk as the disabled set, so finding 2's cache covers both) and the off-main
      predicate mirrors `isSourceEligible` clause for clause. `FeedStoreTests` is green again (109 tests,
      0 failures) and the class that caught it is the regression guard for this pairing.
      Findings 9, 10 and 11 remain.
      Finding 6 (one immutable context per operation) is fixed: `Reservoir.seed` is split into
      `computeSeed` (off-main, mutates nothing) and `commitSeed` (the only write, including
      `markAsSurfaced`), and `reloadFromSQLite`, `promotePreparedCards`, `applyUpdate`'s
      `.append`/`.refresh`/`.flush`/`.trim`, `toggleSource` and `publishCollectionPresetItems`
      validate cancellation and their own inputs after every suspension, carrying the context
      captured where the operation collects its inputs.
      **Not covered by a regression test:** `testComputeSeedDoesNotMutateReservoirUntilCommitted`
      pins the compute/commit split, which is a new API and therefore cannot fail on 1.0 (5). The
      behavioural contract — a superseded operation publishes nothing — needs a controllable
      suspension point, which does not exist yet (finding 10). Do not count that test as coverage
      of finding 6.
      Residual suite flake — measured, attributed, and two concrete leaks fixed. The suite still shows
      **one timing-sensitive failure per run with a moving victim**, and each victim passes
      standalone: `testCollectionPresetSurvivesEditorialRoundTripSlow` (before the fixes),
      `testVideoCategoryFiltering`, `testReloadFromSQLiteFiltersByTaxonomySourceURL`,
      `testManyFeedsCategoryResolution`. On the 1.0 (5) tree the same composition failed
      `testCategoryWithNoItemsShowsEmptyState` instead. The guards are **not** the cause and must not
      be loosened: the log of a reproducing run contains zero `[PresetTrace]` and zero
      `dropping stale` lines, while the same logger's `[TaxonomyTrace]` lines do appear.
      What the log did show, and what was fixed:
      1. `reloadFromSQLite … loaded=0 … taxonomyURLs=1` on the failing leg — a taxonomy URL set no step
         of that test created excluded the item before anything could publish. `FeedStoreTests.tearDown`
         cleared the global filters/taxonomy but `setUp` did not; normalizing the canonical list from
         `resetFiltersForUITestLaunch()` plus `TaxonomyStore.shared.clearSelection()` in `setUp` took
         that reload from `taxonomyURLs=1` to **`taxonomyURLs=0`**.
      2. `Settings.activePreset` (UserDefaults-backed, read by every new store) is now normalized too;
         that alone took `FeedStoreTests` from red on 1.0 (5) to green on that failure.
      **Finding-10 items that remain:** quiesce a store between tests (cancel/await its pipeline,
      preparation, coverage and fetch tasks in `tearDown` — one run shows a fetch for a source from
      another test inside this test's window), give `TaxonomyStore` a full reset, and replace the
      polling-deadline convention (20 s waits, 300 ms debounces) with controllable suspension points,
      which is what finding 10 asks for.

## Feed pipeline: startup and reopen (design of record, 2026-09-16)

Measured on the release candidate rather than assumed. The reported symptoms — empty screens
appearing for no reason, a feed that is rebuilt in front of the user, a reopen that replays the
whole sequence — are not separate bugs. They are one property of the pipeline: **the page that is
shown first is not the page that stays.**

### Invariant: designed, verified in capture, **not landed** (2026-09-16)

`FeedDisplayState` was given a guard refusing a *transient* publication (`settlesPhase: false`) that
would blank a non-empty page, in both the items path and the card path. It was verified in capture —
an 18-frame reopen sequence never lost the page — and then withdrawn, because the withdrawal was
the conservative choice and the record must not overstate why:

- A rule that refuses *every* transient empty publication also refuses the ones that belong to a
  **user-initiated** change of composition (preset/filter), where the old page is wrong and *should*
  go. `settlesPhase: false` does not distinguish that from a rebuild flush, so the guard needs the
  caller's origin (see item 2 below) before it can be trusted.
- That the guard is the **trigger** is proven by an isolated A/B, not inferred: with it,
  `FeedStoreTests.testCollectionPresetSurvivesEditorialRoundTripSlow` fails in 0.559 s; without it,
  it passes in 0.574 s — same tree, serialised, no contention. Independently,
  `FeedmineFilterUITests.testFilterSelectionSurvivesDismissAndReopen` passes without it (46 s) and
  fails with it (35 s).
- The **mechanism is identified** (an earlier note here guessed wrong twice): the test drives
  `setPreset(.collection…)` and then waits `while store.visibleItems.isEmpty` (3 s) before asserting.
  With the guard, the *previous* page stays visible, so that wait exits immediately, the preset's own
  composition has not run yet, and the follow-up assertion
  `store.presetSourceFilter == Set([normalizeURL(externalURL)])` sees `nil`. It is not the early
  `return` skipping persistence: it is the old page masking the wait.
- That also names the real product risk the guard alone would introduce: while a user-initiated
  composition change is in flight, the display can hold the *previous* preset's items while
  `presetSourceFilter` is still unset — the old feed shown under the new preset.
- Consequence for the fix: the guard must skip **only the display mutation** — never the rest of the
  method's work — and must be scoped to publications the user did not ask for.

The invariant's own result stands as evidence for the direction: a transient clear must not blank a
displayed page — but only for publications the user did not ask for.

### Candidate mechanism for the "empty screen for no reason" — fixed defensively (2026-09-16)

The startup watchdog (`FeedStore.start()`, ~line 2138) is a plain inline `if` at the end of `start()`
with no await in front of it — the 20 s and 60 s sleeps above it belong to two *detached* maintenance
tasks. It samples the phase and the loading state at that instant, and its `.idle` branch settles
`.empty`. A transient clear that settles `loadingState` to `.idle` with an empty page can therefore
hit it in the same pass, with the catalogue still loading: a code path that *can* produce the
"No sources enabled" screen the user reported.

Fixed in two places, both defensively:

- the watchdog no longer takes its **empty** branch while `isPreparingInitialRunway` (a page on
  screen still settles `.ready` exactly as before);
- `FeedDisplayState` now settles the loading state by the codebase's own rule for it
  (`FeedStore`: `isPreparingInitialRunway && visibleItems.isEmpty ? .initial : .idle`) in both the
  items and the card path, so a transient clear can no longer claim `.idle` while the runway is
  still being prepared.

Evidence: two 16-frame clean-install captures, the second taken after both fixes, show no empty
screen and monotonic progress — "Preparing your feed" 0 %, then "Loading 1 / 6 / 12 / 14 / 16
sources" 17 → 92 % with the source name rotating underneath. That establishes the absence *after*
the change; there is no pre-fix baseline of the same scenario, so the mechanism is a candidate, not
a proven cause. The rule itself is pinned by
`FeedDisplayStateTests.test_transientClearDuringRunwayPreparation_keepsInitialLoadingState`, which
also asserts that a terminal empty answer still settles `.empty` and that a page on screen still
settles `.idle`.

   together with `PreparedCardLayout` — and rebuild on restore by re-running the pipeline's own
   decode-from-cache path (`CardPreparationCoordinator.decodeToRenderReady`). Never persist or
   rebuild a `UIImage`; the view consumes a decoded image and the pipeline's rule is
   `image ⟺ .hero`, no image ⟺ `.textOnly` ("never publish a placeholder in a hero slot").
   Note: an earlier attempt at this was reverted for simplicity, **not** because the captures proved
   it defective — the hero is hard-bounded to 16:9 in `FeedItemCardView.swift` and the lilac block
   is the drawn content-type placeholder, so the mechanism behind what was seen in build 14 is still
   unidentified and must be reproduced deliberately before this is rewritten.
3. **Append-only background work.** This is the rule that delivers "no updates appearing on screen".
   Background work may only *append below* the displayed prefix; only a user action (filter, preset,
   refresh, shake) may replace what is visible. It belongs in `FeedDisplayState`, the single choke
   point, in the same spirit as `settlesPhase` — a caller-supplied origin, plus a test that publishes
   a different composition over a displayed page and asserts the visible prefix and its order are
   unchanged. Caveat found by reading the view: the screen is keyed off the *phase*, not the items
   (`FeedScreen.swift` renders `InitialFeedLoadingView()` for `.preparing` with no `items.isEmpty`
   check), so a display-level guard alone is not enough — either gate the view or stop entering
   `.preparing` while a page is displayed.
4. **Content/downloads screen.** Make the in-progress state legible and attractive: what is being
   fetched, from where, how far along, and what is already available.
5. **Cold-path budget.** The catalog load is the long pole of a reopen; measure it against the
   "feed visible immediately" requirement with the taxonomy fix in place.

The filter matrix (`FeedmineFilterUITests testFilterCombinationsMatrix`) is a **margin-sensitive
latency probe**, not a reproducer of the empty screen. Run isolated on the current tree it passes

It fails when that podcast figure crosses the 8 s budget under load — yesterday's `[FilterOps] → 0
visible cards` was that margin, not a page that stayed empty. The signal it carries is the latency

Same class of noise, verified the same way: `FeedComposerPreviewTests` passes 5/5 in 1.75 s total
when run alone, and reports 19 s deadline failures only in loaded full-suite runs (alongside

## Feed pipeline: what landed (2026-09-16, second pass)

Three changes are in the tree and verified; one was tried and reverted because it crashed.

**Landed.**

1. **The displayed page is never blanked by a publication the user did not ask for.** `FeedDisplayState`
   refuses an empty publication — transient *or* terminal — while items are on screen, in both the
   items and the card paths. A publication the user asked for (`isUserInitiated`, or the
   `.refreshing` marker `setFilter`/`manualRefresh` already set) replaces the page, which is how a
   filter or preset change takes effect. Pinned by `test_emptyPublicationNeverBlanksADisplayedPage`,
   with `FeedStoreTests.testCollectionPresetSurvivesEditorialRoundTripSlow` and
   `FeedmineFilterUITests.testFilterSelectionSurvivesDismissAndReopen` as acceptance tests for the
   user-action side.
2. **The loading state cannot claim the pipeline is done while the runway is still being prepared**,
   in both paths, using the codebase's own rule (`isPreparingInitialRunway && visibleItems.isEmpty ?
   .initial : .idle`), and the startup watchdog no longer takes its empty branch while the runway
   prepares. Pinned by `test_transientClearDuringRunwayPreparation_keepsInitialLoadingState`.
3. **The view keeps the feed during `.preparing` when there is a page** (`FeedScreen`), because
   `setFilter` and `manualRefresh` both enter `.preparing` and the loading screen used to replace a
   feed the user was reading.

**Reproduction that justified all three.** The app's own log, captured with
`simctl spawn … log show --info --predicate 'process == "feedmine"'`, showed the sequence on a
UI-test launch:

```
loadingState: idle → initial
setVisibleItems firstPaint: phase=ready(contextID: 0)   ← the phase settled
setVisibleItems: items=1 generation=1
setVisibleItems: items=0 generation=2                    ← a publication emptied the page
```

The phase was already `.ready`, so the view chose "No articles yet" — the absence screen the user
reported, with the catalogue still working. The journey capture reproduced it first (`01-main-feed`
empty, "Tip: 6,209 sources are disabled"); after the change the same surface shows cards, and a clean
container shows "Preparing your feed… 0/100" instead.

**Reverted for a crash, do not retry as-is.** Turning a background *replace* into an append (so the
displayed prefix could never be reordered) crashed: `Swift/NativeDictionary.swift:792: Fatal error:
Duplicate values for key: …`, three times, on the filter paths, each right after
`loadingState: idle → refreshing`. A merged page can leave `visibleItems` and `visibleCards`
describing different sets. The rule belongs further down the pipeline than the display: make the
restored page *be* the final page (below) so the pipeline's first publication matches what is already
on screen.

**Journey harness, now actually running.** `feedmineUITests/PersonaExplorationUITests.swift` — the
16-surface user journey (feed, scroll, reader, filters, search, more menu, settings, add feeds,
topics, context menu) — had **no reference in `feedmine.xcodeproj`**, so it never compiled; it also
had a macOS-only optional `screenshot.pngRepresentation` that would have failed to build. Both fixed
(`pngRepresentation` is non-optional `Data` on iOS): it now runs, writes to
`/tmp/feedmine-persona-screenshots`, and 12 surfaces captured with 0 crashes. It stops around the
add-feed step on a non-hittable element, which is harness work, not product.

### Origin: derived, not plumbed

`FeedDisplayState` decides whether a publication was asked for by the user from three sources, so
that getting it wrong at one call site — which is what broke the first two attempts — cannot happen:

1. the explicit `isUserInitiated` flag, for callers that know;
2. the `.refreshing` loading state, which `setFilter`/`manualRefresh` already set;
3. **the phase's own `reason`** (`publicationIsUserInitiated`), which is in scope in both publication
   paths: `.startup` is background work, everything else (`filterChange`, `presetChange`,
   `manualRefresh`, `source`, `collection`) is the user asking for a different composition.

Audit of the sites that deliberately empty the feed: `setFilter`'s two clears are user-initiated via
`.refreshing`; `applyUpdate`'s generation flush is background (keeping the page while
`reloadFromSQLite` republishes is the point); `clearReadHistory` no longer blanks the feed, which is
correct — clearing history is not a request for an empty feed, and later publications re-stamp read
state; `FeedDisplayState.resetAll()` clears unconditionally, so Reset All Data still empties.

### If append-only is attempted again: a merge, not a skip

The reverted attempt dropped same-id re-publications. That is a trap, not a simplification: the
media-retry path republishes the *same id* with an upgraded card (`.textOnly`/placeholder →
`.image` + `.hero` once the image lands), so dropping same-id publications would leave cards stuck on
placeholders forever — worse than the symptom. The rule must be: **for ids already displayed, refresh
the card in place and keep its position; append unseen ids; never remove and never reorder.** Only
then does the displayed prefix survive while the media still arrives.

### The restored page *is* the final page (landed, 2026-09-16)

Two pieces, both proved by fingerprints rather than by eyeballing screenshots (a frame-change count
cannot tell "layout settling" from "the pipeline swapped the page").

1. **Persisted media projection.** The prepared pipeline is the only place that knows a card's image
   cache key, so it now passes `itemID → cacheKey` into the publication; `FeedDisplayState` stores it
   and writes it into the cached page (`CachedPage.cards: [CachedCardMedia]?`, disk-level: a key,
   never an image). On restore, `FeedStore.restoredCards` decodes through
   `mediaAssetStore.decodedImage(for:)` — the same store and the same key space the pipeline uses,
   with the pipeline's own rule (image ⇒ `.hero`; no image ⇒ `.none` + `.textOnly`) — concurrently,
   bounded to the first 30 rows so decoding never sits in front of the first frame.
2. **Upgrade-only merge, in place.** A background batch that has not resolved an image yet must not
   take an image away from a card the reader is looking at. Same ids keep their position; a card that
   *arrives* with media still replaces its media-less predecessor, so the pipeline's own retry path
   keeps working. No set arithmetic, no `uniqueKeysWithValues`, defensive dedup — the reverted
   append-merge crashed exactly there.

Measured on one launch, `page[restore]` vs `page[pipeline]` — identical ids, order, layout and media:

```
page[pipeline] items=13 withMedia=12
page[visible]  items=13 withMedia=12
page[restore]  items=13 withMedia=12
page[pipeline] items=13 withMedia=0     ← a later batch with no resolved media
page[visible]  items=13 withMedia=12    ← the displayed page keeps its images
```

Measured again after two corrections to the merge — it must not `return` (that skipped the
first-paint settle *and* the page-cache write, freezing the cache at the boot batch, which had no
media, so the next launch restored a worse page) and it must order by the **displayed** order rather
than the batch's order — both dimensions now hold across five publications in one warm launch:
ids, order, layout and media identical, and a batch arriving with `withMedia=0` no longer strips the
page:

```
pipeline items=14 media=12  ordem=[72f46fe4, dc0c03b9, e11070c3, d61fc2f5, 44713c0d]
visible  items=14 media=12  ordem=[idêntica]
restore  items=14 media=12  ordem=[idêntica]
pipeline items=14 media= 0  ordem=[idêntica]   ← a batch with nothing resolved
visible  items=14 media=12  ordem=[idêntica]   ← the reader keeps every image, and the order
```

Compare **common prefixes in order**, never equality: the cache can legitimately be shorter (or hold
different content below the fold), and a length difference is benign growth while a difference
*inside* the common prefix is the defect.

Gate after all of it: 460 tests, 0 failures, 0 aborts, 0 crashes.

### Origin, third revision: `.replace` is the user channel

`applyUpdate(.replace(...))` — the channel the code itself documents as "search results, source
toggle, presets; the caller owns the data" — now passes `isUserInitiated: true`, threaded through the
store's `setVisibleItems` wrapper and `promotePreparedCards` into the publication. Without it, turning
off the **last** enabled source (or the last region) publishes an empty replacement while the phase is
`.ready` and the loading state `.idle`, which the new guard would refuse — leaving articles from the
source the user just disabled on screen. The background flush (`.flush`) deliberately keeps the page.

## Latency: where the first paint actually goes (measured 2026-09-16)

Instrumented the `.flush` path that a content-type filter takes, because a filtered page has few
distinct providers and therefore always trips `needsFilteredBreadth` — it fetches over the network and
then reloads the page once more to interleave whatever the fetch added. Two phases, timed:

```
[Latency] flush gen=2 type=video fetchMs=27873 reloadMs=0   reloaded=false sourcesBefore=12 sourcesAfter=16
[Latency] flush gen=3 type=video fetchMs=10827 reloadMs=705 reloaded=true  sourcesBefore=16 sourcesAfter=20
```

- The **awaited network fetch is the whole cost** — 27.9 s and 10.8 s — against a **0.7 s** reload.
- The reload is not waste: `sourcesBefore → sourcesAfter` (12 → 16 → 20) shows the fetch does add
  providers, which is exactly what the interleave-rebuild exists to pick up.
- This is also the source of the media-less batch seen in the reopen work: the second republication
  reuses items whose assets are not resolved yet. The display's upgrade-only merge already keeps that
  invisible; the cost is the time, not the images.

The two steps are already separated by the instrumentation, so they need not be treated as one block:
the reload is **705 ms of a 10.8 s total** (~6 %), the fetch is the rest. The `[TaxonomyTrace] flush
gen=… local page published` → `complete` pair brackets the same window if the timing line is ever
removed.

One real defect in that block, worth fixing on its own even though it is not the latency:
`needsFilteredBreadth` is computed **before** `fetchNextBatch()` and never recomputed after it
(`FeedStore` ~2550-2563), so the second `reloadFromSQLite` runs whenever the *pre-fetch* snapshot was
thin — even when the fetch added no provider at all. That is one extra full republication, and it is
the one that publishes cards whose media is not resolved yet (invisible now thanks to the upgrade-only
merge, but still work). Tightening it needs a signal for "the fetch widened the content type", taken
after the fetch: the page's distinct sources cannot serve as that signal, because the page has not been
republished at that point.

Acceptance for any fix here: `FeedmineFilterUITests.testFilterCombinationsMatrix` — its log prints
"content available: true after N ms" and asserts under 8 s. It failed at 9.7 s and 11.8 s, passed at
6.7 s, so the margin is real and measurable.

**A first fix missed, and why (kept because it is right for its own case).** When a page is already on
screen, the fetch is now started behind it (`startBackgroundBreadthFetch`) instead of being awaited.
Measuring again showed no improvement on the filter case — correctly, because a filter change is
user-initiated and its empty publication is honoured, so `visibleItems` is empty at that moment and the
awaited branch is still taken. The fetch there is not decoration: for a content type the local
database has too little of, it is the only source of the first cards. So the next step is not to move
the fetch but to **stop waiting for the whole breadth of it**: paint as soon as the page's cards are
satisfied instead of after every queued source has been tried.

With the instrumentation extended to report how much of the active type the local page already had:

```
gen=3 type=video localOfType=0   fetchMs=6422  inline=true  reloadMs=6075 items=0
```

## Catalogue is not HTTPS-clean (measured 2026-09-16)

The earlier "the remote search found no `http://` candidates" was wrong; the local scan against the real
files settles it, and it has to touch both places, as the original task note said:

| source | insecure URLs |
|---|---|
| `Resources/Feeds/**/*.opml` (bundled) | **4152** |
| `catalog.sqlite` `catalog_source.declared_url` | **843** |
| `catalog.sqlite` `catalog_source.request_url` | **843** |

Top hosts in the OPML set (which says what a fix would be up against): `feeds.feedburner.com` (301), `rss.castbox.fm` (60), `www.bbc.co.uk` (60), `www.ximalaya.com` (38), `sites.libsyn.com` (24).

**Correction — two claims in the first version of this note were wrong.**

1. These are *not* insecure fetches. The fetch path already upgrades blindly: `FeedHTTPSync.fetch`
   forces `components.scheme = "https"` for any http source URL, and ATS blocks plain HTTP
   (`Info.plist` carries only `NSAllowsArbitraryLoadsForMedia`). So an http `request_url` is a feed that
   *depends on* that upgrade, not a feed fetched in the clear.
2. There is **no http fallback**. Every fetch goes through `RSSFetcher.fetch` → `FeedHTTPSync.fetch`,
   which upgrades unconditionally and returns `.failed` on failure with no retry on the original URL. So
   "https does not validate → leave it alone" would leave a **permanently dead source**, not a working
   one. The earlier note said the app's HTTP validation would cover the remainder; it will not.

The real defect is narrower: hosts that do not serve https, which are unreachable either way. Three
outcomes, decided per URL:

1. https validates → rewrite it in the **OPML/corpus** (the source of truth; `catalog.sqlite` is generated
   by `scripts/build_catalog.py`, with `declared_url`/`request_url` ← `xmlUrl` and `site_url` ← `htmlUrl`,
   so rewriting the .sqlite is overwritten on the next build);
2. no TLS at all → drop the source, or set `default_enabled = 0`; the app can never reach it either way;
3. only then consider a narrow `NSExceptionDomains` — `docs/code-review-pre-publicacao.md` argues against
   the blanket form.

Two artifacts to reconcile while doing it: `site_url` (3 301 rows) is display/attribution only, so only
`request_url`/`declared_url` matter functionally; and `FeedStore.swift:1383` already filters
`request_url LIKE 'https://%'` in one source-selection query, so http rows are first-class in one path and
excluded in another. Acceptance stays the same and is cheap: re-run this scan.

## Product doctrine (user, verbatim intent) — this is the acceptance criterion, not a suggestion

**The front must be calm and stable; the backend must be a hurricane.**

1. The first open **may** be slow — that is what the loading screen is for, as are radical filter changes.
2. The loading screen must be **dynamic and progressive**, showing **what is happening**.
3. **As soon as there is content to show, leave the loading screen and show the feed.**
4. **The feed is sacred.** It only ever contains *ready* content: card assembled, image showing, everything pretty and in
   order. No broken image, no content moving on its own, no scroll jank, no reordering. The feed changes **only when the
   user wants it to change**.
5. **The feed is infinite.** Once it appears and the user scrolls, the next content must already be ready to enter,
   entering without jerks and without disturbing the experience.
6. Facing the user: stable and calm. In the backend: fast, multitasking, and **self-guaranteeing for any situation**.
7. The database fills as fast as possible with content **first inside the current filtering**; once that is complete it
   keeps preparing for **anything that could be asked for**.
8. Given enough time, a filter change updates **only from what is already there** — ready cards, all pretty — and the
   background then starts adjusting to the new reality.
9. **Close and reopen the app: the feed must appear immediately**, from the ready content of the previous interaction.
   "Nobody opens Instagram and waits for Instagram to find content."

### Consequences for the open items

The doctrine makes the filter-change path two different requirements:

### Reopen miss: name the layer before any verdict (absent row vs signature mismatch)

The reopen path is `restoreCachedPage(filterSignature: pageCacheSignature)` (`FeedStore.swift:1856`) — a signature-keyed
lookup. A miss therefore has two different causes, and recording either as "the doctrine fails" before distinguishing them
would misdirect the fix:

- **(a) absent row** — the persisted page was never flushed. Fix belongs to the save path (the persistence guard).
- **(b) signature mismatch** — the page is on disk but the signature computed at relaunch differs from the one it was
  stored under, e.g. preset/region/type come back from UserDefaults asynchronously and the signature is computed before
  that state is rehydrated. This is an **ordering bug in the restore path**, and its fix is entirely different.

So the reopen step must report the stored key(s) and the computed signature as evidence, or state explicitly that it could
not distinguish (a) from (b) — in which case the result is **inconclusive**, not a doctrine verdict. Reading the persisted
store's file from the test side is allowed; product changes are not.

The complete guard set for this one measurement, all of it aimed at making the number trustworthy in both directions:
1. before `terminate()`: prove the page cache is on disk, else inconclusive;
2. before `launch()`: prove the warm precondition, else fail as measurement-invalid;
3. from the instant of launch: sample first-ready-card and loading-surface at the same cadence, never post-hoc;

### RESOLVED: the stall was the container the previous gate left, and the bar is green under a clean-container protocol

The acceptance script now uninstalls the app **between gates** (and again before the journey), and the same three-gate bar
on the same build goes:

```
gate 2: 460 tests, 0 failures in 108.537 s
gate 3: 460 tests, 0 failures in 110.460 s
JORNADA superficies-obrigatorias=17/17 ausentes=[]
```

The gates lost **60–100 s each** along with the failure: 175 → 107 s, 208 → 108 s, 179 → 110 s against the runs whose
container carried the previous gate's state. The unit tests execute inside the app's own process, so they write the app's
UserDefaults and page caches; a store created in that leftover state moves its own generation before the test's debounced
reload matures, the guard `generation == self.filterGeneration` returns silently (`FeedStore.swift:3303`), and the test
waits out a reload that will never run. That is the 36.9–37.1 s stall, and it is a *test-protocol* defect first: each gate
must start from the same container, exactly as a fresh CI run would.

never asked for, and a *user* in that state gets a cleared page with no reload — the same blank-page class as case A's
